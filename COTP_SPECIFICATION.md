## 1. Введение

### 1.1. Что такое COTP

**COTP (Cell-based One-Time Password)** — второй фактор аутентификации, физическим носителем
которого служит **печатная карта 5×5 слов**. Пользователь читает слово из указанной сервером
ячейки (например, `C2`) и предъявляет его вместе с приватным PIN. Сервер хранит **только
секрет карты** и детерминированно **восстанавливает всю сетку** из этого секрета.

Идея аналогична TOTP (RFC 6238) с одной заменой: в TOTP на вход функции подаётся **текущее
время**, а на выходе — **6-значный код**; в COTP на вход подаётся **случайная ячейка** (буква
`A–E` + цифра `1–5`), а на выходе — **слово из фиксированного словаря**. Раз это слово должно
быть напечатано заранее и известно только владельцу карты, индекс слова не может зависеть от
времени: он вычисляется детерминированно из секрета и координаты ячейки. Тогда весь алфавит
ответов (25 слов) можно сгенерировать один раз, напечатать и выдать пользователю.

### 1.2. Бизнес-контекст: «Личный кабинет сотрудника»

| Аспект | Описание |
|---|---|
| Приложение | ПО «Личный кабинет сотрудника», содержит чувствительную личную информацию. |
| Тип сотрудников | **Офисные** — имеют доменную учётную запись; **Рабочие** — доменной учётной записи не имеют. |
| Места входа | **Личный ПК** офисного работника; **публичная стойка** (неттоп с сенсорным экраном). |
| Вход офисных с ПК | По доменной учётной записи, **без второго фактора**. |
| Вход рабочих | **Только** с публичных стоек. |
| Вход офисных со стойки | Разрешён; второй фактор обязателен. |
| Второй фактор на стойке | **Фактор 1** — прикладывание личного RFID-пропуска; **Фактор 2** — **COTP**. |
| Специальные разделы | Защищены дополнительным подтверждением **COTP независимо** от способа входа (ПК или стойка). |

Отсюда следуют требования:
- COTP-карту получают **все, кому нужно**: рабочие (всегда) и офисные (для спец. разделов и
  для входа со стойки).
- RFID-пропуск выступает **identity anchor**: он однозначно идентифицирует сотрудника до
  предъявления второго фактора.
- Даже при входе по домену без второго фактора доступ к спец. разделам требует **step-up**
  через COTP.

### 1.3. Цели и не-цели

**Цели:**
1. Второй фактор, не требующий телефона/сети/батареи у пользователя.
2. Хранение на сервере **только секрета** (не сетки) → детерминированная регенерация карты.
3. Строгая детерминированность и воспроизводимость (математически и тестами).
4. Одноразовость челленджей и защита от replay, перебора и подглядывания.
5. Простая и дешёвая логистика: карта печатается и выдаётся; перевыпуск — секунды.

**Не-цели (важно честно зафиксировать):**
1. COTP **не является** phishing-resistant аутентификатором в смысле FIDO2/WebAuthn. Ответ
   можно перехватить и переиспользовать, пока он не «сгорел» (см. §18).
2. COTP **не заменяет** основную MFA-инфраструктуру, а дополняет её как **deviceless /
   continuity-фактор** (позиция Avatier).
3. COTP **не является** криптотокеном: карта — переносимый **look-up secret** (NIST SP 800-63B,
   §5.1.2), а не вычислительное устройство.

### 1.4. Краткое описание схемы

```
card_secret (256 бит, CSPRNG)
   │
   │  HKDF-SHA-256(salt = card_id, info = "COTP/v1/grid")
   ▼
K_grid ──┐
         │  для каждой ячейки s и nonce n:
         │      label = "COTP/v1/word|" + s.id + "|" + n
         │      h     = HMAC-SHA-256(K_grid, label)
         │      idx   = (h[0]<<8 | h[1]) & (2^11 - 1)   // 0..2047
         └──▶ word = dictionary[idx]   → печатается на карте
```

Сервер сохраняет `card_secret`, `card_id`, версию схемы и хэш PIN. Сетку из 25 слов (или 50,
если используется раскладка TOP/BOTTOM как у Avatier) можно восстановить в любой момент.

## 2. Термины и обозначения

| Термин | Значение |
|---|---|
| **COTP** | Cell-based One-Time Password, данная схема. |
| **card_secret** | Секрет карты (единственный секрет, хранимый на сервере). |
| **card_id** | Публичный идентификатор карты (HKDF salt, печатается на карте). |
| **K_grid** | Ключ вывода индексов слов (HKDF-Expand, info `…/grid`). |
| **K_challenge** | Ключ выбора ячейки в режиме TIME_BASED (info `…/challenge`). |
| **Ячейка (cell)** | Адрес слова: столбец `A–E`, строка `1–5`, позиция (`S`/`T`/`B`). |
| **Слот** | Одна позиция с одним словом; по умолчанию 25 слотов (5×5×1). |
| **Словарь (dictionary)** | Фиксированный список слов размера 2^b (по умолчанию BIP-39, 2048). |
| **Челлендж** | Одноразовый запрос конкретной ячейки. |
| **Burn** | Пометка ячейки/челленджа использованным. |
| **Identity anchor** | Привязка к личности (Employee ID / RFID / SCIM). |
| **PII** | Personally Identifiable Information. |
| **CSPRNG** | Cryptographically Secure PRNG. |
| **HKDF** | HMAC-based KDF, RFC 5869. |
| **Constant-time** | Сравнение без утечки по времени. |

Обозначения: `‖` — конкатенация; `|x|` — длина; `2^b` — степень двойки; `<<`/`>>` —
битовые сдвиги; `&` — побитовое И; `⊕` — XOR.

## 3. Криптографические примитивы

| Примитив | Выбор | Стандарт | Обоснование |
|---|---|---|---|
| Хэш-MAC | **HMAC-SHA-256** | RFC 2104, FIPS 198-1 | Доступен в JDK (`javax.crypto.Mac`), стойкость ≥ SHA-1. |
| KDF | **HKDF-SHA-256** | RFC 5869 | Разделяет один секрет на независимые под-ключи. |
| CSPRNG | **SecureRandom** | FIPS 140 | Генерация секретов и случайных ячеек. |
| KDF для PIN | **PBKDF2-HMAC-SHA256** | RFC 8018, NIST SP 800-132 | Ноль зависимостей (есть в JDK). |
| Сравнение | **constant-time XOR** | — | Защита от timing-атак на слово/PIN. |
| Кодирование | **Base32** | RFC 4648 §6 | Резервное копирование/провижининг секрета. |

**Почему HMAC-SHA-256, а не SHA-1?** COTP — новая схема, обратная совместимость с OATH не
нужна. SHA-256 даёт 32 байта выхода, что удобно для извлечения ≥11 бит и для HKDF.

**Почему HKDF?** Один секрет порождает два независимых ключа (`K_grid`, `K_challenge`) и
привязан к `card_id` как к salt: смена `card_id` при том же секрете даёт другую сетку
(защита от переиспользования секретов при перевыпуске).

## 4. Модель угроз

### 4.1. Активы

- `card_secret` и производные ключи (компрометация = компрометация всех карт).
- Слова на карте (переносимый look-up secret).
- PIN (низкоэнтропийный knowledge-фактор).
- Identity anchor (RFID / Employee ID).
- Действия в спец. разделах (цель атаки).

### 4.2. Доверенные границы

- **Сервер** — доверенная зона; хранит `card_secret` (шифрованным at-rest) и PIN-хэш.
- **Печатная карта** — недоверенный носитель у пользователя.
- **Публичная стойка** — недоверенная среда (kiosk mode, считыватель RFID, экран).
- **Канал** — обязан быть TLS; иначе возможен перехват челлендж/ответ.

### 4.3. Угрозы и контрмеры

| Угроза | Описание | Контрмера COTP | Покрытие |
|---|---|---|---|
| **Replay челленджа** | Повтор ответа на ранее выданный челлендж | `challengeId` one-time + TTL | §11 |
| **Replay ячейки** | Повторное использование одной ячейки | `BurnPolicy.CELL` (по умолчанию) | §11 |
| **Перебор PIN** | Онлайн-подбор | throttling/lockout across-session (RFC 4226 §7.3, NIST 800-63B) | §11.4 |
| **Подбор слова** | Угадывание слова из 2048 | высокая энтропия секрета + throttling | §18 |
| **Shoulder-surfing** | Подглядывание карты/ввода | случайная ячейка + burn + PIN | §18.2 |
| **Копирование карты** | Фото/копия сетки | PIN + burn + revocation | §18.3 |
| **Перехват канала** | MITM видит челлендж+ответ | TLS + (опц.) challenge-response с временем | §18.1 |
| **Компрометация сервера** | Утечка `card_secret`/PIN-хэшей | шифрование at-rest, KMS/HSM, PoLP | §18.5 |
| **Race condition** | Двойное использование ячейки | атомарный check-and-set в `BurnStore` | §11.5 |
| **DoS/throttle-bypass** | Сброс счётчика новой сессией | счётчик привязан к карте, не к сессии | §11.4 |
| **Enumeration** | Перебор `card_id` | не раскрывать существование карты | §18.6 |

### 4.4. Вне модели угроз

- Атаки на кliент с полным контролем над ОС пользователя (keylogger).
- Физическое принуждение владельца карты.
- Компрометация RFID-считывателя на уровне, обходящем сервер (покрывается первым фактором
  как таковым, но не является предметом COTP).

## 5. Генерация секрета

### 5.1. Требования

- **[НОРМА]** Длина секрета ≥ **128 бит** (RFC 4226 R6); **[РЕКОМ]** **256 бит**.
- **[НОРМА]** Источник — **CSPRNG** (`java.security.SecureRandom`).
- **[НОРМА]** Секрет **уникален** для каждой карты.
- **[РЕКОМ]** Секрет хранится **зашифрованным at-rest** (AES-GCM/KMS/HSM), расшифровывается
  только на момент генерации сетки/верификации.

### 5.2. [АЛГОРИТМ] Определение генерации

```
function generate_secret(byteLen = 32):
    # byteLen = ceil(bits / 8); рекомендуемые 32 байта = 256 бит
    s = new byte[byteLen]
    SecureRandom().nextBytes(s)
    return s
```

### 5.3. Резервное копирование и провижининг

Секрет переносится в **Base32** (RFC 4648 §6, алфавит `A–Z2–7`), без паддинга:

```
secret Base32 (пример для вектора §14) =
AAAQEAYEAUDAOCAJBIFQYDIOB4IBCEQTCQKRMFYYDENBWHA5DYPQ
```

> **[НОРМА]** Base32-представление секрета — конфиденциально; его нельзя печатать на карте.
> На карте печатается только `card_id`.

## 6. Вывод ключей (HKDF, RFC 5869)

### 6.1. [АЛГОРИТМ]

```
PRK       = HKDF-Extract(salt = UTF8(card_id), IKM = card_secret)
K_grid    = HKDF-Expand(PRK, info = UTF8("COTP/v1/grid"),      L = 32)
K_challenge = HKDF-Expand(PRK, info = UTF8("COTP/v1/challenge"), L = 32)
```

- `HKDF-Extract(salt, IKM) = HMAC-SHA-256(salt, IKM)` (RFC 5869 §2.2).
- `HKDF-Expand(PRK, info, L)`: `T(0) = ∅`, `T(i) = HMAC-SHA-256(PRK, T(i-1) ‖ info ‖ byte(i))`,
  `OKM = (T(1) ‖ T(2) ‖ …)` длиной `L` (RFC 5869 §2.3).
- **[НОРМА]** `PRK` имеет длину не менее 32 байт (требование RFC 5869 §2.3).

### 6.2. Зачем два ключа

- `K_grid` — вывод индексов слов (печатная карта).
- `K_challenge` — выбор ячейки в режиме `TIME_BASED`; независим от `K_grid`, чтобы знание
  одного не помогало в другом.

Привязка к `card_id` через `salt` делает ключи **специфичными для карты**: одинаковый секрет
на разных картах даёт разные сетки. Это **проверено** тестом (§14: «different cardId … alters
the grid»).

## 7. [АЛГОРИТМ] Функция получения индекса слова — ядро COTP

### 7.1. Канонический label

Для ячейки `s` (например `C2`) и счётчика разрешения коллизий `nonce` (начинается с 0):

```
label(s, nonce) = "COTP/v1/word|" + s.id + "|" + nonce
```

где `s.id` — канонический адрес (`"A1"…"E5"`; при раскладке TOP/BOTTOM — `"A1T"…"E5B"`).
Строка кодируется в **UTF-8**. Формат фиксирован и является частью контракта версии `v1`.

### 7.2. Вычисление

```
h     = HMAC-SHA-256(K_grid, UTF8(label(s, nonce)))
value = (h[0] & 0xFF) << 8 | (h[1] & 0xFF)        # 16 старших бит
index = value & (2^b - 1)                          # b = log2(|dictionary|)
word  = dictionary[index]
```

Для стандартного словаря BIP-39: `b = 11`, `2^11 = 2048`, `index ∈ [0, 2047]`.

### 7.3. Отсутствие модульного смещения

Обычные схемы `HMAC mod N` дают смещение, если `N` не делит `2^k`. В COTP этого нет:
- словарь имеет размер **степень двойки** `2^b`;
- `value` — 16 равномерно распределённых бит (выход HMAC неотличим от случайного);
- младшие `b` бит равномерного 16-битного значения **равномерны** на `[0, 2^b)`;
- следовательно, `index` равномерен **без rejection-сэмплинга**.

Это **проверено** статистически (§14, тест равномерности: 4 корзины по 2000 из 8000 — в
пределах 15 %).

### 7.4. Псевдокод

```
function word_index(K_grid, cell, nonce, dictionary_bits):
    label = "COTP/v1/word|" + cell.id + "|" + nonce
    h     = HMAC_SHA256(K_grid, utf8(label))       # 32 байта
    value = (h[0] << 8) | h[1]
    return value & ((1 << dictionary_bits) - 1)
```

## 8. [АЛГОРИТМ] Построение сетки 5×5

### 8.1. Канонический порядок

Слоты обходятся в **фиксированном порядке**: столбцы в заданном конфигурацией порядке (по
умолчанию `A,B,C,D,E`), внутри — строки (`1..5`), внутри — позиции (`S`; либо `T,B`).
Порядок — **часть контракта детерминированности**.

### 8.2. Разрешение коллизий

Слово может повториться (вероятность для 25 слов из 2048 ≈ 14 %, для 50 ≈ 45 %). Чтобы слова
на карте были **уникальны**, применяется детерминированное разрешение: при коллизии `nonce`
инкрементируется и хэш пересчитывается до первого неиспользованного слова.

### 8.3. [АЛГОРИТМ] Псевдокод

```
function build_grid(K_grid, config):
    used = {}
    grid = ordered_map()
    for cell in config.cells_in_canonical_order():
        nonce = 0
        loop:
            idx = word_index(K_grid, cell, nonce, config.dictionary_bits)
            word = config.dictionary[idx]
            if word not in used:
                break
            nonce = nonce + 1
        grid[cell.id] = word
        used.add(word)
    return grid
```

Для референсного вектора (§14) коллизий не возникло: финальные слова совпадают с `nonce=0`.

### 8.4. Стоимость

25–50 HMAC-операций на восстановление карты — микросекунды. Сервер может восстановить сетку
при каждом челлендже, либо кэшировать её (кэш не является источником истины).

## 9. Детерминированность — доказательство

### 9.1. Формулировка

**Утверждение.** `Grid = G(secret, card_id, config)` — чистая (детерминированная) функция.
Для любых двух вызовов с одинаковыми аргументами результат побитово совпадает.

### 9.2. Леммы

**Лемма 1 (детерминированность HKDF).** `HMAC-SHA-256` — детерминированная функция ключа и
сообщения (RFC 2104). `HKDF-Extract` и `HKDF-Expand` состоят только из вызовов HMAC с
фиксированными входами (включая постоянный счётчик блока), следовательно `PRK`, `K_grid`,
`K_challenge` детерминированы при фиксированных `(secret, card_id, version)`.
*Доказательство.* Прямая композиция детерминированных функций; `info` и `salt` фиксированы
конфигурацией. ∎

**Лемма 2 (детерминированность индекса).** `word_index(K_grid, cell, nonce)` — чистая функция:
`label` формируется однозначно из `cell.id` и `nonce`; `HMAC` детерминирован (Лемма 1);
извлечение бит — детерминированная битовая операция. ∎

**Лемма 3 (детерминированность разрешения коллизий).** Обход слотов задан фиксированным
линейным порядком. Индукция по слоту `i`: множество `used_i` определяется только предыдущими
слотами; проверка `word ∉ used_i` и инкремент `nonce` — детерминированные операции. Значит
для слота `i` значение `word_i` единственно. ∎

**Лемма 4 (терминация).** `nonce` ограничен константой (`MAX_COLLISION_NONCE = 10^6`); при
`|dictionary| = 2048` и ≤50 словах коллизии разрешаются с подавляющей вероятностью за
несколько попыток; в противном случае генерируется исключение (детерминированный отказ). ∎

### 9.3. Теорема

По Леммам 2–4 `build_grid` возвращает единственную детерминированную сетку для заданных
`(K_grid, config)`, а по Лемме 1 `K_grid` детерминирован при фиксированных
`(secret, card_id, version)`. Следовательно `G` детерминирована. ∎

### 9.4. Следствия

1. Серверу достаточно хранить `(card_id, secret, version, layout)` — сетка регенерируема.
2. Перевыпуск карты при том же секрете и новом `card_id` даёт **другую** сетку (Лемма 1).
3. Любое изменение словаря, порядка слотов, label или версии меняет сетку → требует смены
   `version` и перевыпуска (нормативный запрет менять контракт «на месте»).

### 9.5. Эмпирическое подтверждение

В среде сбора выполнены (**[ПРОВЕРЕНО]**):
- 200 случайных карт (25 слов) — повторный вывод даёт идентичную сетку; слова уникальны
  внутри карты;
- референсный вектор с фиксированным секретом воспроизводится побитово (`K_grid`, индексы,
  слова) — см. §14;
- смена одного бита секрета меняет сетку; смена `card_id` при том же секрете меняет сетку;
- HKDF сверен с официальным тест-вектором RFC 5869 Test Case 1.

## 10. Челлендж (генерация запроса ячейки)

Челлендж — объект с полями `challengeId`, `cardId`, `cell`, `mode`, `issuedAt`, `expiresAt`.

### 10.1. Режим RANDOM (по умолчанию)

```
available = все слоты, кроме уже сожжённых (при BurnPolicy.CELL)
if available пусто: ошибка "card exhausted"
cell = available[ SecureRandom().nextInt(|available|) ]   # равномерно, без смещения
```

`SecureRandom.nextInt(n)` равномерен — rejection-сэмплинг не нужен.

### 10.2. Режим TIME_BASED (TOTP-подобный, опциональный)

```
T = floor(epochSeconds / stepSeconds)            # stepSeconds по умолчанию 30
# равномерный выбор слота методом rejection над HMAC-потоком:
attempt = 0
repeat:
    label = "COTP/v1/challenge|" + T + "|" + attempt
    h     = HMAC-SHA-256(K_challenge, UTF8(label))
    v     = (h[0]<<24)|(h[1]<<16)|(h[2]<<8)|h[3]      # 32-бит беззнаковое
    limit = floor(2^32 / slotCount) * slotCount
    attempt = attempt + 1
until v < limit
index = v mod slotCount
cell  = cells[index]
```

Даёт **stateless** выбор ячейки (сервер восстанавливает её из времени). При верификации ячейка
принимается, только если совпадает с детерминированным выбором для **любого** шага в окне
`[nowStep − timeWindowBack, nowStep + timeWindowForward]`; таким образом окно — реальный
ограничитель дрейфа/реплея (а не «мёртвый» параметр). **[СТАНДАРТ-родственно]** HOTP/TOTP
(RFC 4226/6238).

> **[НОРМА]** При `challengeMode = TIME_BASED`:
> - `BurnPolicy.CELL` и `BurnPolicy.COOLDOWN` **несовместимы** с `TIME_BASED` (детерминированная
>   ячейка будет отвергнута при повторном использовании). Если пользователь выбрал `TIME_BASED`
>   и не задал политику явно, по умолчанию применяется `BurnPolicy.CHALLENGE`; явная комбинация
>   `TIME_BASED + CELL/COOLDOWN` отвергается при сборке `CotpPolicy`;
> - срок жизни челленджа ограничивается сверху **остатком окна валидности**:
>   `ttl = min(challengeTtl, (issueStep + timeWindowBack + 1)·step − now)`, поэтому «живой, но
>   непроверяемый» челлендж не возникает, а при `timeWindowBack=0` TTL всё равно положителен
>   (текущий шаг). Значения по умолчанию: `timeStep=30`, `timeWindowBack=4`, `timeWindowForward=1`,
>   `challengeTtl=120`.

### 10.3. TTL и идентификатор

- `challengeId` — 128 бит CSPRNG, Base32 (26 символов без паддинга).
- TTL — по умолчанию **120 секунд** (конфигурируемо); по истечении челлендж отвергается.
- Челлендж одноразов (см. §11).

### 10.4. Почему случайная ячейка, а не раскладка?

Avatier использует случайную координату + TOP/BOTTOM; COTP обобщает это до случайного слота.
Раскладка TOP/BOTTOM поддержана конфигурацией (`positions = [TOP, BOTTOM]`) для
совместимости с ICC-подобной печатью. **[AVATIER]**

## 11. Верификация

### 11.1. Факторы

1. **Possession** — слово, прочитанное с карты (проверяется constant-time).
2. **Knowledge** — PIN (PBKDF2-хэш); опционально.
3. **Identity anchor** — RFID/Employee ID/SCIM; опционально.

### 11.2. [АЛГОРИТМ] Порядок проверок

```
verify(card, pinHash, challenge, word, pin, presentedId, registeredId, now):
    if null-аргументы или challenge.cardId != card.cardId:   return INVALID_REQUEST
    cardScheme = card.scheme()                  # версия/раскладка/словарь берутся У КАРТЫ
    if card.expiresAt != null и now >= card.expiresAt:       return CARD_EXPIRED
    if challenge.expired(now):                               return CHALLENGE_EXPIRED
    if challenge.mode == TIME_BASED:
        if cell != time_derived_cell(cardCfg, now ± окно):      return INVALID_REQUEST
    if cell not in card.grid:                                return INVALID_REQUEST
    if throttle.locked(cardId) и not expired:                return THROTTLED
    if burnStore.challengeUsed(challenge.id):                return CHALLENGE_REUSED
    if policy == CELL:
        if |burnStore.burnedCells(cardId)| >= cardScheme.slotCount: return CARD_EXHAUSTED
        if burnStore.cellUsed(cardId, cell):                 return CELL_ALREADY_USED
    if identity передана (непустые значения):
        if presentedId != registeredId:                      return IDENTITY_MISMATCH   # без throttle
    expected = regenerate_grid(cardCfg, card.secret).get(cell.id)
    if not constant_time_eq(word, expected):                 failure → INVALID_WORD
    if pinHash != null и not verify_pin(pin, pinHash):       failure → INVALID_PIN
    # успех — атомарно; результат check-and-set ОБЯЗАН проверяться:
    if not burnStore.markChallengeUsed(cardId, challenge.id): return CHALLENGE_REUSED
    if policy == CELL и not burnStore.markCellBurned(cardId, cell): return CELL_ALREADY_USED
    throttle.reset(cardId)
    return OK
```

> **Примечания к реализации (v1.0):**
> - **Схема** (версия/раскладка/словарь/шаг времени) всегда берётся из **`card.scheme()`** — как
>   при верификации, так и при генерации челленджа. Карта, выпущенная под другой версией или
>   раскладкой, проверяется корректно, а не молча даёт `INVALID_WORD`; несовпадение раскладок
>   между генератором и верификатором невозможно. **Политики** (burn/TTL/throttle/PIN) берутся из
>   конфигурации компонента.
> - Для `TIME_BASED` ячейка **обязана** совпадать с детерминированным выбором для любого шага в
>   окне `[nowStep − timeWindowBack, nowStep + timeWindowForward]`; произвольная/устаревшая/
>   «слишком будущая» ячейка отвергается (`INVALID_REQUEST`).
> - **Кардинальность:** при `CELL` сначала проверяется исчерпание (`burnedCells >= slotCount` →
>   `CARD_EXHAUSTED`), затем конкретная ячейка (`CELL_ALREADY_USED`). Генератор при исчерпании
>   бросает `CardExhaustedException`.
> - **Identity anchor** не является секретом: `IDENTITY_MISMATCH` **не** увеличивает счётчик
>   неудач PIN (иначе знание табельного номера позволяло бы блокировать карту). Пустой/отсутствующий
>   anchor означает «не проверяется».
> - Неизвестная (вне раскладки) ячейка → `INVALID_REQUEST`.
> - Счётчик неудач инкрементируется **атомарно** (check-and-increment); `markChallengeUsed(cardId, id)`
>   и `markCellBurned(...)` — атомарные check-and-set с обязательной проверкой результата.
> - `BurnStore.reset(cardId)` очищает и сожжённые ячейки, и использованные челленджи карты.

### 11.3. Политики burn

| Политика | Что сжигается | Ёмкость карты | Когда применять |
|---|---|---|---|
| `CELL` (default) | Ячейка + челлендж | `slotCount` успешных проверок, затем re-enroll | Строгий one-time, как у Avatier; логин на киоске, service desk. **Несовместима с `TIME_BASED`** (см. §10.2) |
| `COOLDOWN` | Только челлендж; ячейка — на «перезарядке» `cellCooldown` | не ограничена (ячейки переиспользуемы после cooldown) | Компромисс для частых входов (десятки/день): одна ячейка не показывается повторно в течение `cellCooldown` (по умолчанию 24 ч), что снижает ценность подсмотренного ответа. **Несовместима с `TIME_BASED`** |
| `CHALLENGE` | Только челлендж | не ограничена (ячейки переиспользуемы немедленно) | Частый step-up; обязателен PIN + временное окно |
| `NONE` | Ячейки не сжигаются | не ограничена | Только тесты/stateless TIME_BASED. **Важно:** `challengeId` всё равно помечается использованным (защита от replay конкретного челленджа), т.е. «NONE» относится только к ячейкам. |

> **[AVATIER]** «Each authentication uses a unique, one-time challenge value… Used values are
> permanently invalidated and never reused» → соответствует `BurnPolicy.CELL`.

### 11.4. Throttling / lockout

- **[НОРМА]** Счётчик неудач привязан к `cardId` и **не сбрасывается новой сессией**
  (RFC 4226 §7.3).
- По умолчанию: `maxFailures = 5`, затем `lockDuration = 15 минут`.
- После успешной проверки счётчик сбрасывается.
- **[СТАНДАРТ]** Согласовано с NIST SP 800-63B (ограничение попыток, throttling).

### 11.5. Constant-time и гонки

- Слово и PIN сравниваются constant-time (`ConstantTime`).
- `BurnStore.markCellBurned`/`markChallengeUsed` — атомарные check-and-set: параллельные запросы не
  могут оба получить `OK`. `recordCellUse` (окно `COOLDOWN`) — обычная (last-write) запись метки
  времени и **не** является жёстким one-time: под `COOLDOWN` one-time обеспечивает атомарная пометка
  челленджа.
- Рекомендация: в кластере — распределённое хранилище (Redis/БД) с транзакционным `SETNX`.

### 11.6. Результаты верификации

`OK`, `INVALID_WORD`, `INVALID_PIN`, `IDENTITY_MISMATCH`, `CHALLENGE_EXPIRED`,
`CHALLENGE_REUSED`, `CELL_ALREADY_USED`, `CARD_EXPIRED`, `CARD_EXHAUSTED`, `THROTTLED`,
`INVALID_REQUEST`.

> **[РЕКОМ]** Во внешний интерфейс не отдавать различающиеся тексты ошибок (защита от oracle),
> но для внутреннего аудита и UX — различать.

### 11.7. Клиент-безопасный результат (anti-oracle)

Детальные `VerificationResult` — **внутренние** (аудит/метрики/UX). Для внешнего ответа используйте
`VerificationResult.toClientError()` → `ClientError`:

| `ClientError` | Из `VerificationResult` | Сообщение |
|---|---|---|
| `NONE` (успех) | `OK` | OK |
| `AUTHENTICATION_FAILED` | `INVALID_WORD`, `INVALID_PIN`, `IDENTITY_MISMATCH`, `CHALLENGE_REUSED`, `CELL_ALREADY_USED`, `CARD_EXHAUSTED` | «Authentication failed» |
| `CHALLENGE_EXPIRED` | `CHALLENGE_EXPIRED` | «Challenge expired» |
| `CARD_EXPIRED` | `CARD_EXPIRED` | «Card expired» |
| `TOO_MANY_ATTEMPTS` | `THROTTLED` | «Too many attempts» |
| `BAD_REQUEST` | `INVALID_REQUEST` | «Bad request» |

**[НОРМА]** Все фактор-специфичные отказы (слово/PIN/identity/replay) схлопываются в единый
`AUTHENTICATION_FAILED`, чтобы клиент не мог различить, какой фактор не совпал.

## 12. PIN и identity anchor

### 12.1. PIN

- **[НОРМА]** Хранится только **PBKDF2-HMAC-SHA256**-хэш (RFC 8018), формат
  `pbkdf2-sha256$<iterations>$<salt B64>$<hash B64>`, 16-байтная соль, 256-битный выход.
- **[РЕКОМ]** Итерации ≥ 210 000 (OWASP baseline); в идеале — Argon2id (вне JDK, при наличии
  BouncyCastle).
- **[НОРМА]** Низкая энтропия PIN → **обязателен** throttling/lockout (§11.4).
- Длина PIN — политикой приложения (рекомендуется ≥ 6 цифр; у Avatier в демо 4). **[AVATIER]**

### 12.2. Identity anchor

- RFID-пропуск / Employee ID / SCIM-principal.
- **[НОРМА]** Верификация COTP проверяет совпадение предъявленного и зарегистрированного
  identity, если приложение его передаёт.
- **[НОРМА]** Проверка **fail-closed на стороне приложения**: если приложение обязано
  обеспечивать identity anchor, оно должно передавать **непустые** значения с обеих сторон.
  Библиотека трактует пустой/отсутствующий anchor как «не проверяется» (пропуск проверки), а
  `IDENTITY_MISMATCH` **не** влияет на throttle PIN (identity не является секретом и не должен
  позволять блокировать карту).
- Сравнение identity — точное после `trim()` (с учётом регистра); значения-идентификаторы должны
  приводиться к каноническому виду на стороне приложения.
- На печатной карте **нет PII** (только `card_id`) — требование Avatier. **[AVATIER]**

### 12.3. Шифрование секрета at-rest (SecretCipher)

- **[НОРМА]** `card_secret` хранится на сервере **только в зашифрованном виде**; расшифровка —
  на момент генерации сетки/проверки.
- Абстракция `SecretCipher` (`encrypt`/`decrypt` + Base64-хелперы) отделяет ядро от конкретного
  хранилища ключей. Реализации:
  - `AesGcmSecretCipher` (в комплекте, JDK-only): AES-256-GCM, свежий 96-битный IV на каждое
    шифрование, тег 128 бит, формат `IV ‖ ciphertext+tag`;
  - KMS/HSM-адаптер (AWS KMS / Azure Key Vault / HashiCorp Vault) реализует тот же интерфейс
    вызовом `Encrypt`/`Decrypt` — выносится в отдельный опциональный модуль (чтобы ядро
    оставалось zero-dependency).
- **[РЕКОМ]** Ключ AES либо хранится в KMS/HSM и инжектируется при старте, либо сама операция
  делегируется в KMS; поддерживается ротация ключа.

## 13. Словарь

### 13.1. Требования

- **[НОРМА]** Размер словаря — **степень двойки** `2^b`, `256 ≤ 2^b ≤ 65536`.
- **[НОРМА]** Слова уникальны (в том числе **без учёта регистра** — сравнение при аутентификации
  регистронезависимо), без пробелов и пустых строк. Запрещены любые пробельные и
  формат-символы Unicode (неразрывный пробел `U+00A0`, zero-width space `U+200B`, BOM `U+FEFF`).
- **[РЕКОМ]** Слова короткие, различимые, легко произносимые (для service desk по телефону).

### 13.2. Базовый словарь

Используется **BIP-39 English** (2048 слов, 11 бит/слово) — тот же класс словарей, что и для
сид-фраз криптокошельков. Он встроен в ресурсы библиотеки
(`src/main/resources/ru/loolzaaa/cotp-english.txt`).

### 13.3. Замена словаря

- Допускается свой словарь (например, локализованный) при соблюдении §13.1.
- **[НОРМА]** Смена словаря меняет сетку **всех** карт → обязательна смена `version` и
  перевыпуск (см. Лемма 1/Следствие 3).
- Словарь хранится в конфигурации/ресурсе и версионируется вместе со схемой.

```
[RFID reader] ──► [Kiosk client] ──TLS──► [API Gateway / BFF]
                                               │
                        ┌──────────────────────┼──────────────────────┐
                        ▼                      ▼                      ▼
                 [Identity Service]     [COTP Service]         [Audit]
                 (RFID→employee,        (challenge/verify,      (события)
                  AD, SCIM)              burn/throttle store)
                                               │
                                        [Secrets: KMS/HSM]
```

### 16.2. Сценарий A — вход на публичной стойке (рабочие и офисные)

1. Сотрудник прикладывает RFID-пропуск → `Identity Service` резолвит `employeeId`
   (identity anchor, **фактор 1**).
2. `COTP Service` выдаёт челлендж: `{challengeId, cell, expiresAt}`.
3. Киоск показывает ячейку, например **`C2`**.
4. Сотрудник читает слово с карты и вводит **слово + PIN**.
5. `verify(...)`; при успехе — сессия/токен. При `BurnPolicy.CELL` ячейка сгорает.

### 16.3. Сценарий B — step-up для спец. разделов (независимо от способа входа)

1. Пользователь уже аутентифицирован (домен на ПК **или** RFID+COTP на стойке).
2. При входе в защищённый раздел приложение запрашивает **свежий COTP-челлендж**.
3. Пользователь предъявляет слово + PIN.
4. При успехе выдаётся **короткоживущий step-up токен** (scope = раздел), привязанный к
   `employeeId` и сроку.

> Даже офисный работник на своём ПК (вход по домену без 2FA) обязан пройти COTP для
> спец. раздела — как и требуется в постановке.

### 16.4. Enrollment / re-enroll / revocation

- **Enrollment**: `generateCard(cardId)` → сохранить `{cardId, secret(enc), pinHash, employeeId}`;
  напечатать `grid` и выдать. Для рабочих — в процессе выдачи пропуска; для офисных — через IT.
- **Re-enroll**: при исчерпании ячеек (`CARD_EXHAUSTED`), утере, или политике срока —
  `generateCard(newCardId, newSecret)`; старую карту `revoke`.
- **Revocation**: пометить карту `REVOKED`; очистить `BurnStore`/`ThrottleStore`; при
  необходимости перевыпустить.
- **Срок действия**: `expiresAt` на карте; напоминания по политике. **[AVATIER]**

### 16.5. [ПРЕДЛОЖЕНИЕ] REST API (эскиз)

```
POST /cotp/challenge
  req:  { employeeId, context: "kiosk-login" | "stepup:<section>" }
  resp: { challengeId, cell: "C2", expiresAt }

POST /cotp/verify
  req:  { challengeId, word, pin }
  resp: { result: "OK", stepUpToken? }            # 200; иначе 401 + reason (внутр.)

POST /cotp/enroll            (admin/HR)
  req:  { employeeId }
  resp: { cardId, cardPdfUrl, expiresAt }         # secret НЕ возвращается наружу

POST /cotp/{cardId}/revoke   (admin/security)
```

### 16.6. Модель данных (сервер)

```
COTP_CARD(
  card_id        PK,
  employee_id    FK,
  scheme_version,               -- "COTP/v1"
  layout,                       -- SINGLE | WORD_PAIRS
  card_secret    (encrypted),
  pin_hash,
  status         ACTIVE|REVOKED|EXPIRED,
  created_at, expires_at
)
COTP_BURN(card_id, cell_id, used_at)         -- при BurnPolicy.CELL
COTP_CHALLENGE_USED(challenge_id, used_at)   -- one-time
COTP_THROTTLE(card_id, failures, locked_until)
COTP_AUDIT(id, employee_id, card_id, event, result, ts, ip, context)
```

**Персистентность карты.** Для хранения/переноса серверной части карты используйте
`CotpCredential` (`cardId` + `secret` + `schemeId` + сроки) и `CotpCredentialCodec`
(однострочный формат `COTP1|…|CRC32` с контролем опечаток). Схема восстанавливается по версии через
`SchemeRegistry`; сетка не хранится — регенерируется `credential.toCard(registry)`. Закодированное
значение содержит секрет → хранить **зашифрованным** (`SecretCipher`), не логировать.

### 16.7. Политики (рекомендуемые)

| Параметр | Значение по умолчанию | Комментарий |
|---|---|---|
| Раскладка | SINGLE (25) или WORD_PAIRS (50) | 25 даёт меньше переиспользований. |
| BurnPolicy | `CELL` для киоска/service desk; `CHALLENGE`/`COOLDOWN` для частого step-up | см. §11.3 |
| cellCooldown | 24 ч | только для `COOLDOWN`. |
| TTL челленджа | 120 с | короче — безопаснее. |
| maxFailures / lockout | 5 / 15 мин | across-session. |
| PIN | ≥ 6 цифр, PBKDF2 ≥ 210k | повышает стойкость. |
| Срок карты и ротация | 180–365 дней; плановый перевыпуск (напр. раз в 90 дней) | с напоминаниями; перевыпуск = новый `card_id` + новый `card_secret` + `BurnStore.reset`. |
| Транспорт | TLS 1.2+ | обязательно. |

#### Таблица «сценарий → BurnPolicy»

| Сценарий | Частота | Рекомендация |
|---|---|---|
| Вход на публичной стойке (рабочие, офисные) | десятки/день | `COOLDOWN` (напр. 24 ч) или `CHALLENGE` + ротация раз в 2–4 недели |
| Step-up спец. разделов | несколько/день | `COOLDOWN` (короче, напр. 1–4 ч) или `CHALLENGE` |
| Service desk / восстановление доступа | редко, высокая чувствительность | `CELL` (строгий one-time, как у Avatier) |
| Резервный/air-gapped сценарий | редко | `CELL` |

> **Мягкий лимит челленджей на сутки** и сигналы аномалий — задача наблюдаемости/аудита
> (`cotp-metrics` и SIEM), а не жёсткого контроля в ядре (см. P1 в `TODO.md`).

### 16.8. Аудит-события (`CotpEventSink`)

Ядро эмитит типизированные события через `CotpEventSink` (по умолчанию `NOOP`), которые питают
SIEM/аудит и модуль метрик (`cotp-metrics`, P1). События не содержат секретов, слов, PIN или
`challengeId`; допускается публичный `cardId` (sink может хэшировать/опускать его).

`CotpEvent(type, at, cardId, context, mode, cellId, result)`; `context` — свободный контекст
приложения (например `"kiosk_login"`, `"stepup"`), проставляется при выдаче челленджа и
переносится в события верификации.

| `CotpEventType` | Когда | Поля |
|---|---|---|
| `CHALLENGE_ISSUED` | выдана ячейка | `mode`, `cellId`, `context` |
| `VERIFY_SUCCEEDED` | успешная проверка | `result=OK` |
| `VERIFY_FAILED` | отказ (см. `result`) | `result` (INVALID_WORD/PIN, …) |
| `CHALLENGE_REUSED_ATTEMPT` | replay `challengeId` | `result=CHALLENGE_REUSED` |
| `CARD_EXHAUSTED` | нет доступных ячеек | `result=CARD_EXHAUSTED` |
| `CELL_BURNED` | ячейка сожжена (`CELL`) | `cellId` |
| `CELL_COOLDOWN_RECORDED` | ячейка на cooldown (`COOLDOWN`) | `cellId` |
| `THROTTLE_LOCKOUT` | карта заблокирована после серии неудач | `context` |

Использование: `new Cotp(scheme, policy, eventSink)` или
`new CotpVerifier(policy, burnStore, throttleStore, eventSink)`.
**[НОРМА]** sink обязан быть потокобезопасным, быстрым и не логировать секреты.

### 16.9. Фасад и политика по контексту

Фасад `Cotp` убирает бойлерплейт:

```java
Cotp cotp = new Cotp(CotpScheme.defaults(), CotpPolicyResolver.defaults());
CotpEnrollment enr = cotp.enroll("CARD-ID", pin);                 // card + pinHash + credential
CotpChallenge ch = cotp.challenge(enr.card(), "kiosk_login", now); // policy по контексту
VerificationResult r = cotp.authenticate(enr.card(), enr.pinHash(), ch, word, pin, now);
ClientError client = r.toClientError();                            // anti-oracle, наружу
```

`CotpPolicyResolver` выбирает политику по контексту (`kiosk_login` → `COOLDOWN` 24 ч;
`stepup` → `CHALLENGE` 60 с; `service_desk` → `CELL`), разделяя burn/throttle-store и схему карты.
Типизированные исключения: `CotpConfigurationException` (подтип `IllegalArgumentException` — ошибки
схемы/политики/словаря/credential), `CotpCryptoException` и `CardExhaustedException` (подтипы
`CotpException`).

## 17. Сравнение с HOTP/TOTP/OCRA и Avatier ICC

| Свойство | HOTP (4226) | TOTP (6238) | OCRA (6287) | **COTP** | Avatier ICC |
|---|---|---|---|---|---|
| Вход | counter | время | challenge Q + PIN P | секрет + **ячейка** | карта + координата |
| Выход | 6–8 цифр | 6–8 цифр | цифры/алф. | **слово из словаря** | слово |
| Носитель | токен/приложение | приложение | токен | **бумага** | бумага |
| Вычислитель у клиента | да | да | да | **нет** | нет |
| Хранение сервером | секрет | секрет | секрет | **только секрет** | секрет/сетка |
| One-time | counter | окно | challenge | **burn** | burn |
| Phishing-resistant | нет | нет | частично | **нет** | нет |
| Статус | RFC | RFC | RFC | **проект** | продукт |

**Что стандарт, что проект:** примитивы (§3) — стандарт; композиция «сетка из секрета»,
функция индекса, canonical label, порядок слотов, burn-семантика — **[ПРЕДЛОЖЕНИЕ]**. Механика
«печатная карта + координата + PIN + identity anchor» — **[AVATIER]** (вдохновение).

### 17.1. Совместимость по духу

COTP сознательно повторяет структуру TOTP: `code = F(secret, input)`, но `input` — не время,
а ячейка, а `code` — слово. В отличие от TOTP, COTP-ответ **нельзя** вычислить на клиенте без
предварительно напечатанной карты, и он проверяется сравнением со значением из
детерминированно восстановленной сетки.

## 18. Безопасность: детальный разбор

### 18.1. Перехват канала и replay

- Без TLS ответ (слово+PIN) и челлендж перехватываются.
- **Контрмеры**: TLS; `challengeId` one-time; TTL; burn ячейки; в TIME_BASED — временное окно.
- **[ПРЕДЛОЖЕНИЕ]** Для критичных операций можно требовать **две** ячейки в одном челлендже
  (ответ = два слова), что снижает ценность единичного перехвата.

### 18.2. Реконструкция карты при наблюдении (главное ограничение)

COTP — **look-up secret**: каждая наблюдаемая пара (ячейка, ответ) раскрывает значение этой
ячейки. Собрав ответы максимум для `N` разных ячеек, наблюдатель восстанавливает всю сетку и
перестаёт зависеть от подсматривания (хотя ему всё ещё нужен PIN).

**Контрмеры:**
- `BurnPolicy.CELL` — одна ячейка используется один раз; после `N` успехов карта исчерпывается
  и подлежит перевыпуску. Это **ограничивает** общее число наблюдений.
- Короткий срок жизни карты и ротация.
- Требование двух и более ячеек на операцию.
- Мониторинг аномалий (много челленджей на карту за короткое время).
- **Честное позиционирование**: COTP — не FIDO2; это усиление за счёт possession+knowledge.

> Это фундаментальное свойство всех карточных/grid-схем (NIST «look-up secret»), а не дефект
> конкретной реализации. Avatier решает это burn-ом и сроком жизни карты. **[AVATIER]**

### 18.3. Копирование и утеря карты

- Фото сетки + знание PIN = полная компрометация до burn/revoke.
- **Контрмеры**: PIN как отдельный секрет (не на карте); burn; мгновенный `revoke`; отсутствие
  PII на карте (карта без PIN «бесполезна»). **[AVATIER]**

### 18.4. Shoulder-surfing на стойке

- Наблюдение за экраном (ячейка) и вводом (слово+PIN).
- **Контрмеры**: случайная ячейка; PIN; приватность ввода (скрытый ввод PIN); burn; обучение.
- Полностью устранить наблюдение всего процесса нельзя.

### 18.5. Компрометация сервера / БД

- Утечка `card_secret` → все карты. PIN-хэши защищены PBKDF2, но не спасают от офлайн-подбора
  слабых PIN.
- **Контрмеры**: шифрование секретов at-rest (KMS/HSM), минимум привилегий, ротация секретов,
  отдельное хранение PIN-хэшей, аудит доступа.

### 18.6. Брутфорс и enumeration

- Онлайн-перебор слова (1/2048) и PIN (1/10^k) — throttling/lockout обязателен.
- Не раскрывать существование `card_id`/`employeeId`.

### 18.7. Гонки и параллелизм

- Атомарный check-and-set в `BurnStore`/`ThrottleStore` (Redis `SETNX`, БД `SELECT ... FOR
  UPDATE`/unique constraint).

### 18.8. Что COTP не защищает

- Фишинг/real-time MITM (ответ можно релеить, как любой OTP) — до burn.
- Захват конечной точки (keylogger).
- Социальная инженерия против service desk без identity anchor.

### 19.3. Пример

```java
Cotp cotp = new Cotp();                                   // 5x5, BIP-39, SHA-256
CotpCard card = cotp.generateCard(cotp.newCardId());
String pinHash = cotp.newPinHash("1234".toCharArray());

Instant now = Instant.now();
CotpChallenge ch = cotp.challengeGenerator().random(card, now, cotp.verifier().burnStore());
VerificationResult r = cotp.verifier().verify(
        card, pinHash, ch, card.wordAt(ch.cell()), "1234".toCharArray(), now);
assert r == VerificationResult.OK;
```

Раскладка Avatier (TOP/BOTTOM, 50 слов) — это часть **схемы**; политика задаётся отдельно:

```java
CotpScheme scheme = CotpScheme.builder()
    .positions(List.of(CellPosition.TOP, CellPosition.BOTTOM))
    .build();
CotpPolicy policy = CotpPolicy.builder()
    .burnPolicy(BurnPolicy.COOLDOWN)
    .cellCooldown(Duration.ofHours(24))
    .build();
Cotp cotp = new Cotp(scheme, policy);
```

## 21. Открытые вопросы / будущие версии

1. **Реконструкция сетки при наблюдении** — фундаментальное ограничение; для частых операций
   рассмотреть обязательные **две ячейки** и/или короткий срок жизни карты. **[ПРОБЕЛ/дизайн]**
2. **Argon2id для PIN** вместо PBKDF2 (требует BouncyCastle; сейчас ноль зависимостей).
3. **Распределённые BurnStore/ThrottleStore** (Redis/БД) — интерфейсы готовы, реализаций под
   кластер в библиотеке нет.
4. **QR/Apple-Wallet-версия карты** — вне текущего объёма.
5. **Service-desk offline-режим** — Avatier заявляет локальную проверку; COTP-модель требует
   наличия секрета у проверяющего (локальная реплика/HSM). **[ПРОБЕЛ]**
6. **Локализация словаря** (RTL/CJK) — словарь заменяем, но нужна проверка читаемости.
7. **Формальный аудит** схемы и threat-model review.

## Приложение A. Полный псевдокод COTP v1

```
# --- Провижининг ---
function enroll(card_id, layout, dictionary):
    secret = CSPRNG(32)                                 # 256 бит
    PRK = HKDF_Extract(salt=UTF8(card_id), IKM=secret)
    K_grid = HKDF_Expand(PRK, info=UTF8("COTP/v1/grid"), 32)
    grid = build_grid(K_grid, layout, dictionary)
    store(card_id, encrypt(secret), scheme="COTP/v1", layout)
    return grid                                          # печатается

# --- Челлендж ---
function challenge(card_id):
    card = load(card_id)
    available = slots(layout) minus burned(card_id)      # BurnPolicy.CELL
    cell = available[ SecureRandom().nextInt(len(available)) ]
    id = Base32(CSPRNG(16))
    return {id, cell, expiresAt = now + TTL}

# --- Верификация ---
function verify(challenge, word, pin):
    card = load(challenge.card_id)
    if challenge.expired():                 return CHALLENGE_EXPIRED
    if locked(card_id):                     return THROTTLED
    if challenge_used(challenge.id):        return CHALLENGE_REUSED
    if cell_used(card_id, challenge.cell):  return CELL_ALREADY_USED
    expected = word_for(card, challenge.cell)             # regenerate grid
    if not constant_time_eq(word, expected): record_failure(); return INVALID_WORD
    if not verify_pin(pin, card.pin_hash):   record_failure(); return INVALID_PIN
    mark_challenge_used(challenge.id)
    mark_cell_used(card_id, challenge.cell)               # if BurnPolicy.CELL
    reset_throttle(card_id)
    return OK

# --- Восстановление сетки ---
function word_for(card, cell):
    K_grid = HKDF_Expand(HKDF_Extract(salt=UTF8(card.id), IKM=card.secret),
                         info=UTF8("COTP/v1/grid"), 32)
    return build_grid(K_grid, card.layout, dictionary)[cell.id]

function build_grid(K_grid, layout, dict):
    used = {}
    for cell in layout.canonical_order():
        nonce = 0
        while true:
            h = HMAC_SHA256(K_grid, UTF8("COTP/v1/word|" + cell.id + "|" + nonce))
            idx = ((h[0] << 8) | h[1]) & (len(dict) - 1)
            if dict[idx] not in used: break
            nonce += 1
        grid[cell.id] = dict[idx]
        used.add(dict[idx])
    return grid
```

## Приложение C. Отличия от Avatier Identity Challenge Card

| Аспект | Avatier ICC | COTP |
|---|---|---|
| Словарь/размер | неизвестен | BIP-39, 2048 (степень двойки) |
| Хранение сервером | неизвестно (возможно, сетка) | **только секрет** |
| Слова на ячейку | 2 (TOP/BOTTOM) | 1 (default) или 2 (совместимый режим) |
| Генерация сетки | не раскрыта | **HKDF + HMAC-SHA-256, детерминированная** |
| Челлендж | случайная координата | RANDOM или TIME_BASED |
| One-time | burn значений | `BurnPolicy.CELL` / `CHALLENGE` |
| Алгоритм ответа | не раскрыт | **специфицирован, с тест-векторами** |
| Позиционирование | deviceless MFA | deviceless second factor (look-up secret) |

Итог: COTP воспроизводит **наблюдаемую механику** ICC (печатная сетка + координата + PIN +
identity anchor), но заменяет нераскрытый алгоритм Avatier на **открытый, детерминированный и
проверяемый** криптографический конвейер на стандартных примитивах.
