# COTP — модель угроз (threat model)

> **Статус.** Проектный документ для пилота, сверенный с `COTP_SPECIFICATION.md` (v1.0) и кодом
> `cotp-java/`. Оценки вероятности/влияния — качественные (Низкая / Средняя / Высокая) и
> предназначены для приоритизации, а не для количественного risk-менеджмента.
> **Язык:** русский; идентификаторы алгоритмов, имена RFC, классы и URL — в латинице.
> **Дата:** 2026-10-06.

---

## 1. Область и метод

Документ описывает угрозы для **COTP** — второго фактора на печатной карте 5×5 слов,
применяемого в сценариях «Личного кабинета сотрудника» (киоск-вход и step-up спец. разделов).
Анализ ведётся по:

- **активам** (§2),
- **акторам** (§3),
- **доверенным границам** (§4),
- **потоку данных** (§5),
- категориям **STRIDE** для каждой угрозы (§6),
- отдельно — **фундаментальному ограничению look-up secret** (§7).

Приняты только те контрмеры, которые реально существуют в спецификации или коде. Всё, что
является планом, помечено как **[ПРЕДЛОЖЕНИЕ/ПЛАН]** (со ссылкой на `TODO.md`).

## 2. Активы

| Актив | Описание | Где находится | Компрометация означает |
|---|---|---|---|
| `card_secret` | 256-битный секрет карты; единственный секрет, хранимый сервером | Сервер (зашифрован at-rest) | Все карты: сетка восстанавливаема |
| `K_grid`, `K_challenge` | производные ключи (HKDF-SHA-256, RFC 5869) | Только в памяти процесса | То же, что `card_secret` |
| Слова сетки | Переносимый **look-up secret** на карте | Печатная карта у пользователя | Possession-фактор карты |
| PIN | Низкоэнтропийный knowledge-фактор | В голове пользователя; на сервере — только PBKDF2-хэш | Knowledge-фактор |
| `pin_hash` | `pbkdf2-sha256$…` | Сервер | Ускорение офлайн-подбора PIN |
| Identity anchor | RFID-пропуск / Employee ID / SCIM | Инфраструктура / пользователь | Спуфинг личности (фактор 1) |
| Действия в спец. разделах | Цель атаки (доступ к чувствительным данным) | Приложение | Нарушение конфиденциальности/целостности |
| Состояние burn/throttle | `BurnStore`/`ThrottleStore` | Сервер (in-memory/stores) | Повторное использование / обход lockout |
| Аудит | События `challenge/verify` | Сервер / SIEM | Низкая (данные без секретов/PII) |

## 3. Акторы

| Актор | Возможности | Мотивация |
|---|---|---|
| Легитимный владелец карты | Знает PIN, читает слово, знает RFID | Доступ |
| Наблюдатель/shoulder-surfer | Видит экран киоска и ввод рядом с пользователем | Доступ, кража карты |
| Злоумышленник с копией карты | Фото сетки, PIN подбирает/подсматривает | Доступ |
| Внешний сетевой атакующий (MITM) | Перехват/релей канала | Доступ |
| Инсайдер / администратор | Доступ к серверу, БД, KMS-политикам | Доступ/утечка |
| Компрометированный сервер/БД | Чтение шифротекста `card_secret`, PIN-хэшей | Все карты, офлайн-подбор |
| DoS-атакующий | Массовые запросы challenge/verify | Нарушение доступности |
| Скомпрометированный киоск/endpoint | Keylogger, подмена UI | Перехват ответов |

## 4. Доверенные границы и допущения

```
[RFID reader] ──► [Kiosk client] ──TLS 1.2+──► [API Gateway / BFF]
  (недоверн.)        (недоверн.)                    │  доверенная зона
                                       ┌────────────┼────────────┐
                                       ▼            ▼            ▼
                               [Identity Service] [COTP Service] [Audit/SIEM]
                                                    │
                                             [KMS/HSM]
```

**Границы доверия:**

| Зона | Доверие | Комментарий |
|---|---|---|
| Сервер (COTP Service, БД, KMS) | Доверенная | Хранит `card_secret` (шифрованным) и `pin_hash`; PoLP |
| Печатная карта | Недоверенный носитель | Пользователь может копировать; нет PIN |
| Публичная стойка (kiosk) | Недоверенная среда | Экран, ввод, считыватель RFID |
| Канал | Обязан быть TLS | Иначе перехват челлендж/ответ |
| RFID-считыватель | Полу-доверенный (фактор 1) | Атаки, обходящие сервер, вне области (§4.4) |

**Допущения (assumptions):**

1. Сервер и его хранилища находятся под контролем организации; доступ администрируется (PoLP).
2. Все внешние взаимодействия идут по **TLS 1.2+**; терминация TLS — на доверенном шлюзе.
3. Часы сервера синхронизированы (NTP): TTL челленджа и режим `TIME_BASED` критичны ко времени.
4. `SecureRandom` JDK пригоден для CSPRNG; примитивы (`javax.crypto`) не скомпрометированы.
5. KMS/HSM доступен и ключ AES инжектируется при старте (для `AesGcmSecretCipher`) либо операция
   делегируется в KMS **[ПЛАН]** (`TODO.md` P2-H).
6. Карта доставляется владельцу по доверенному каналу; **PIN передаётся/задаётся отдельно и не
   печатается**; на карте нет PII (только `card_id`).
7. Пользователь хранит PIN в секрете и защищает карту от копирования.
8. Ответы (слово/PIN) не логируются приложением (**[НОРМА]** спецификации).

## 5. Поток данных и ключевые доверительные предположения

### 5.1. Сценарий A — вход на публичной стойке (§16.2)

1. Сотрудник прикладывает RFID → `Identity Service` резолвит `employeeId` (фактор 1).
2. `COTP Service` **выдаёт челлендж** `{challengeId, cell, expiresAt}` (`ChallengeMode.RANDOM` по
   умолчанию; ячейка — равномерный CSPRNG-выбор, `CotpChallengeGenerator.random`).
3. Киоск показывает ячейку (например `C2`).
4. Пользователь **читает слово с карты** и вводит **слово + PIN**.
5. `CotpVerifier.verify(...)`: сервер снова выводит `K_grid` из `card_secret` и сравнивает слово
   constant-time (`ConstantTime.wordsMatch`); при успехе — `BurnStore.markChallengeUsed(...)` и
   (для `CELL`) `markCellBurned(...)`, `ThrottleStore.reset(...)`.

### 5.2. Сценарий B — step-up спец. разделов (§16.3)

1. Пользователь уже аутентифицирован (домен/ПК или RFID+COTP на стойке).
2. Приложение запрашивает **свежий COTP-челлендж** (тот же серверный поток).
3. Пользователь предъявляет слово + PIN.
4. При успехе — короткоживущий step-up токен (scope = раздел), привязанный к `employeeId`.

### 5.3. Ключевые доверительные предположения (trust assumptions)

| # | Предположение | Почему критично | Что при нарушении |
|---|---|---|---|
| TA-1 | **Сервер сам генерирует челлендж** и хранит его `challengeId`/`expiresAt` | Одноразовость и привязка ячейки | Подмена ячейки/replay |
| TA-2 | **Пользователь читает слово именно с карты**, а не подбирает | Possession-фактор | Подбор слова 1/2048 (§18.6) |
| TA-3 | **Слово+PIN идут только по TLS** | Иначе MITM видит ответ | Перехват (до burn) |
| TA-4 | Слово сравнивается **constant-time**, результат — из `card.scheme()` | Защита от timing и рассинхрона раскладок | Oracle/`INVALID_WORD` при верной карте |
| TA-5 | `BurnStore`/`ThrottleStore` **атомарны и переживают конкуренцию** | Одноразовость, lockout | Двойное использование ячейки |
| TA-6 | `card_secret` хранится **только зашифрованным** (`SecretCipher`) | Компрометация БД | Все карты |
| TA-7 | На карте **нет PII** и **нет PIN** | Утеря карты не раскрывает личность | Спуфинг/компрометация |

## 6. STRIDE-анализ

Легенда: **Вер.** — правдоподобность, **Вл.** — влияние, **§** — раздел спецификации.
Контрмеры указаны по фактическому коду/спеке; плановое — помечено.

### 6.1. Spoofing / Repudiation

| # | Угроза (STRIDE) | Вер. | Вл. | Существующая контрмера (механизм, §) | Остаточный риск |
|---|---|---|---|---|---|
| S1 | Ответ не от владельца: копия карты + наблюдение PIN | Сред. | Выс. | PIN как отдельный секрет (не на карте) + burn + revocation (§18.3) | До burn/revoke злоумышленник может войти |
| S2 | MITM/фишинг релеит challenge+response в реальном времени | Сред. | Выс. | TLS + одноразовый `challengeId` + TTL + burn ячейки (§18.1, §11) | Релей успешен до первого burn; COTP **не** phishing-resistant (§1.3) |
| S3 | Клонирование RFID (фактор 1) | Сред. | Сред. | COTP — независимый фактор 2; identity anchor (§12.2) | Клон даёт только фактор 1; атаки ниже сервера — вне области (§4.4) |
| S4 | Enumeration `card_id`/`employeeId` для подбора цели | Низ. | Сред. | Не раскрывать существование карты; одинаковые внешние ответы (§18.6, §11.6) | Конкретная реализация внешнего API — на приложении; `toClientError()` **[ПЛАН]** (P2-C) |
| R1 | Владелец отрицает операцию | Сред. | Сред. | Аудит-модель задана (§16.6 `COTP_AUDIT`) | **События/`CotpEventSink` ещё не реализованы** (`TODO.md` P1-A) → аудита нет |
| R2 | Откат/потеря состояния burn после рестарта (in-memory) | Сред. | Выс. | Атомарный check-and-set; контракт распределённых stores (§11.5) | `InMemory*Store` теряет состояние при рестарте; нужен `cotp-redis`/`cotp-jdbc` **[ПЛАН]** (P2-G) |

### 6.2. Tampering / Elevation of privilege

| # | Угроза (STRIDE) | Вер. | Вл. | Существующая контрмера (механизм, §) | Остаточный риск |
|---|---|---|---|---|---|
| T1 | Изменение `card_secret` в БД | Низ. | Выс. | AES-256-GCM, тег 128 бит (`AesGcmSecretCipher`, §12.3) | Ошибка конфигурации ключа; `SECRET_DECRYPT_FAILURE` — событие **[ПЛАН]** (P1-A) |
| T2 | Подмена ячейки/`cardId` в челлендже | Низ. | Выс. | TLS; `challenge.cardId == card.cardId` иначе `INVALID_REQUEST`; одноразовый id (§11.2) | Если приложение принимает челлендж не от сервиса |
| T3 | Race: два параллельных запроса на одну ячейку/челлендж | Низ. | Сред. | Атомарные `markChallengeUsed`/`markCellBurned` с проверкой результата (§11.5) | Только при неатомарном/распределённом store без транзакций |
| T4 | Офлайн-подбор слабого PIN при утечке БД | Сред. | Выс. | PBKDF2-HMAC-SHA256, ≥210 000 итераций, соль 16 Б (`PinHasher`, §12.1) | Короткий/цифровой PIN подбираем; Argon2id — **[ПЛАН]** (P3-A) |
| E1 | Компрометация сервера → все `card_secret` | Низ. | Выс. | Шифрование at-rest, KMS/HSM, PoLP, ротация (§18.5) | Доступ к KMS = расшифровка всех карт; KMS-адаптер **[ПЛАН]** (P2-H) |
| E2 | Перебор слова (1/2048) | Сред. | Сред. | Throttling/lockout across-session (`maxFailures=5`, `lockDuration=15m`); `CELL` дополнительно исчерпывает карту (§18.6, §11.4) | При `CHALLENGE`/`NONE` частые попытки ограничены только throttle |

### 6.3. Information disclosure

| # | Угроза | Вер. | Вл. | Существующая контрмера (механизм, §) | Остаточный риск |
|---|---|---|---|---|---|
| I1 | Реконструкция всей сетки по наблюдениям (главное ограничение) | Сред. | Выс. | Случайная ячейка + burn (`CELL`) / cooldown (`COOLDOWN`) + ротация + PIN (§18.2) | Фундаментально: N наблюдений ⇒ вся сетка; см. §7 ниже |
| I2 | Shoulder-surfing на стойке (экран+ввод) | Выс. | Сред. | Случайная ячейка, скрытый ввод PIN, burn, обучение (§18.4) | Полностью не устраним |
| I3 | Утечка `card_secret`/`pin_hash` из БД/логов | Низ. | Выс. | Шифрование at-rest; PBKDF2 для PIN; **[НОРМА]** не логировать секреты/PII (§18.5, §12) | Ошибки логирования приложения |
| I4 | Timing-oracle на слово/PIN | Низ. | Сред. | `ConstantTime` для слова и PIN (§11.5) | Порядок проверок различает состояния; внешние тексты ошибок — **[РЕКОМ]** generic (§11.6); `toClientError()` **[ПЛАН]** (P2-C) |
| I5 | Различение исходов как oracle (`CHALLENGE_REUSED`, `CELL_ALREADY_USED`, …) | Сред. | Сред. | Внутренний `VerificationResult`; **[РЕКОМ]** не отдавать различающиеся тексты (§11.6) | Зависит от интеграции; хелпер маппинга **[ПЛАН]** (P2-C) |
| I6 | Утечка секрета через Base32-бэкап | Низ. | Выс. | **[НОРМА]** Base32-секрет конфиденциальен, не печатается (§5.3) | Нарушение при ручном обращении |

### 6.4. Denial of service

| # | Угроза | Вер. | Вл. | Существующая контрмера (механизм, §) | Остаточный риск |
|---|---|---|---|---|---|
| D1 | Онлайн-перебор PIN → блокировка карты | Сред. | Сред. | `ThrottleStore` across-session, `maxFailures`/`lockDuration`; счётчик привязан к карте, не к сессии (§11.4) | Легитимный пользователь блокируется атакующим, знающим `cardId`; `IDENTITY_MISMATCH` намеренно не throttle (§11.2) |
| D2 | Массовые `CARD_EXHAUSTED` → поток перевыпусков | Низ. | Сред. | `BurnPolicy.CELL` ограничивает; мониторинг — **[ПЛАН]** (§16.7, P1-B) | Автоматического rate-limit на перевыпуск в ядре нет |
| D3 | Флуд `challenge`/`verify` | Сред. | Сред. | TTL; внешний rate-limit — **[ПЛАН]** (P2-F) | Ядро не ограничивает частоту запросов |
| D4 | «Выучить» карту серией челленджей | Сред. | Выс. | `CELL` исчерпывает карту; cooldown замедляет; сигналы аномалий — **[ПЛАН]** (P1-B) | Без мониторинга серия наблюдений остаётся незамеченной |

## 7. Ограничение look-up secret: реконструкция сетки

COTP — это **look-up secret** (NIST SP 800-63B §5.1.2): ответ на челлендж — не вычисляемое на
клиенте значение, а **предварительно напечатанное** слово. Следствие (честно зафиксировано в
§1.3 и §18.2 спецификации):

> Каждая наблюдаемая пара **(ячейка, слово)** раскрывает значение этой ячейки. Собрав ответы
> максимум для `N` различных ячеек, наблюдатель восстанавливает **всю** сетку и далее не зависит
> от подсматривания — хотя ему всё ещё нужен **PIN**.

Это фундаментальное свойство **всех** карточных/grid-схем, а не дефект реализации; Avatier
решает его burn-ом и сроком жизни карты.

**Существующие контрмеры:**

| Контрмера | Механизм в COTP | Эффект |
|---|---|---|
| `BurnPolicy.CELL` | Ячейка сжигается после успеха (`BurnStore.markCellBurned`) | Максимум `slotCount` (25/50) успешных наблюдений до `CARD_EXHAUSTED` |
| `BurnPolicy.COOLDOWN` | Ячейка не показывается повторно в течение `cellCooldown` (по умолчанию 24 ч) | Замедляет накопление разных ячеек |
| Рандомный челлендж | `SecureRandom` выбор ячейки | Наблюдатель не выбирает, какую ячейку раскрыть |
| Ротация и срок жизни | `expiresAt` + перевыпуск (новый `card_id`+`card_secret`) | Ограничивает окно накопления |
| PIN | отдельный knowledge-фактор | Знания сетки недостаточно |
| Мониторинг аномалий | **[ПЛАН]** события/метрики P1-A/P1-B | Обнаружение серий «изучения» |

**Не реализовано (предложение):**

- **Multi-cell challenge** — требовать **две и более** ячейки на операцию, что снижает ценность
  единичного наблюдения. Статус: **[ПРЕДЛОЖЕНИЕ]**, `TODO.md` P3-C; в коде отсутствует.
- **Argon2id** для PIN — повышает стоимость офлайн-подбора `pin_hash`. **[ПЛАН]** P3-A.
- **Offline-верификация service desk** (локальная реплика секрета/HSM) — открытый вопрос §21;
  увеличивает поверхность утечки, если не реализован на HSM. **[ПРОБЕЛ]** P3-E.

**Остаточный риск:** при достаточном числе успешных наблюдений (для `CELL` — до 25) и знании PIN
злоумышленник получает полный доступ до перевыпуска/ротации. Для высокоценных операций следует
применять `CELL`, короткий срок жизни и (в будущем) multi-cell.

## 8. Сводка остаточных рисков

| Риск | Причина | Принятие / что делать |
|---|---|---|
| Релей ответа до burn | COTP не phishing-resistant | Принять; не использовать COTP как единственный фактор для критичных операций без step-up/ротации |
| Реконструкция сетки наблюдением | look-up secret | Принять; `CELL`/`COOLDOWN` + ротация; реализовать multi-cell (P3-C) |
| Потеря burn/throttle при рестарте (in-memory) | `InMemory*Store` | В пилоте — один узел; для кластера реализовать P2-G и durable TTL |
| Отсутствие аудита/метрик | P1-A/P1-B не реализованы | Не вводить в прод без событий/аудита; закрыть P1-A/P1-B |
| Офлайн-подбор PIN | низкая энтропия PIN | PIN ≥ 6 цифр; Argon2id (P3-A); изоляция `pin_hash` |
| Оракул исходов | `VerificationResult` наружу | Реализовать generic-ответ приложения (P2-C) |
| Компрометация KMS | доверие к KMS | PoLP, аудит доступа к KMS, ротация ключей |
| Дрейф часов | TTL/`TIME_BASED` | NTP-мониторинг; окно `timeWindowBack`/`Forward` |

## 9. Вне области (out of scope)

- Атаки на клиент с полным контролем над ОС пользователя (**keylogger**, вредоносный браузер).
- Физическое принуждение владельца карты.
- Компрометация RFID-считывателя на уровне, **обходящем сервер** (покрывается фактором 1, но не
  предмет COTP).
- Фишинг / real-time MITM как класс (ответ можно релеить, как любой OTP) — до burn.
- Социальная инженерия против service desk **без** identity anchor.
- Компрометация JDK/JCE-провайдера, `SecureRandom`, KMS/HSM как доверенных примитивов.
- Атаки на цепочку печати/доставки карты (принтер, PDF-генератор, курьер) — ответственность
  процесса, не ядра; PDF/QR — отдельный модуль **[ПЛАН]** (U-C).
- Инфраструктурный DoS (сетевой флуд, отказ БД/Redis) — уровень платформы.
- Неверная реализация приложения-интегратора (логирование секретов, слабый PIN-полиси,
  передача `VerificationResult` наружу) — покрывается интеграционным гайдом (Q-E) и P2-C/P2-F.
